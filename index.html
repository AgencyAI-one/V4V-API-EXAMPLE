Studio bulk generation

POST /studio/batches — up to 300 products in one JSON request (body ≤ 1 MiB). Each item becomes its own Studio workflow with its own task, results and credit accounting; an invalid item fails on its own while the rest continue. Field names are the same as for POST /studio; override precedence is item → batch → Studio defaults. If an item has both product_id and product_url, the library product wins, and fields set explicitly in input override imported values.

Bulk shares the server generation queue with ordinary requests, which go first. By default one bulk workflow runs per account at a time, and all of an account's batches share that slot. Acceptance reserves nothing. Each item's estimate is held only when that item is admitted to start, and max_credits caps spent plus held credits. Items can show an empty attempts array until the next worker tick.

Required (1–200 characters). If you leave it empty, one is generated. The same key with identical JSON returns the same batch, so retries are safe. A changed body under that key returns 409 IDEMPOTENCY_CONFLICT.

Batches

GET /studio/batches?offset&limit — this account's batches, newest first · GET /studio/batches/{batch_id}?offset&limit — item progress, paged by zero-based item index (limit ≤ 100) · POST /studio/batches/{batch_id} — pause / resume (+ a higher max_credits) / cancel, and the paid retry_failed / rework / restart, which add new attempt versions to the same batch. A batch reports completed once the latest version of every item is terminal, and completed batches can still contain failed items.

Open a batch

The docs ask for no more than one poll every five seconds. A completed attempt carries signed result links; open it in Tasks (or GET /tasks/{task_id}) to renew them once they expire.

Pause and cancel stop future starts. Attempts that were already admitted keep their reservations and finish. Resume continues after a sample, a top-up or a budget increase, and the budget can only go up. Cancel stops the remaining items. A cancelled batch can't resume, but it can still restart or rework terminal items (below). Controls are idempotent while the batch state is unchanged. Resume never retries failed attempts.

New attempts paid · each operation needs a new Idempotency-Key

Empty fields keep the item's previous request. Setting product_id clears the old product_url, and the other way round. Item input / parameters win over the operation-wide changes below.
0 B / 1 MiB
A key belongs to one operation on this batch. After a network error, send the same key and body again (safe). After a success the field clears, so the next operation gets a new key. The same key with a changed body returns 409 IDEMPOTENCY_CONFLICT.
